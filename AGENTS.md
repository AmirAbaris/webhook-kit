# Repository Guidelines (`webhook-kit`)

This file defines mandatory conventions for humans and AI coding agents contributing to the `webhook-kit` repository.

## Project Structure & Modules

- `src/`: Library source (TypeScript, ESM-first, zero runtime dependencies).
  - `crypto/`: Web Cryptography API (`crypto.subtle`) primitives (`computeSubtleHmac`, `timingSafeEqual`, hex/base64 helpers).
  - `utils/`: Internal and shared utilities (`extractRawBody`).
  - `providers/`: First-party webhook provider adapters (`stripe.ts`, `github.ts`, `shopify.ts`).
  - `verify.ts`: Generic webhook verification (`verifyWebhookSignature`, `assertWebhookSignature`).
  - `errors.ts`: Structured error hierarchy (`WebhookKitError`, `SignatureVerificationError`, `TimestampToleranceError`, etc.).
  - `types.ts`: Shared TypeScript contracts.
  - `index.ts`: Public package entrypoint re-exporting public APIs.
- `bin/`: Zero-dependency CLI binary (`bin/webhook-kit.mjs`).
- `tests/`: Vitest runtime test suites (`tests/*.test.ts`) and tarball sandbox test (`tests/package-smoke.mjs`).
- `tests-d/`: `tsd` compile-time type narrowing tests (`tests-d/*.test-d.ts`).
- `docs/`: Consumer-facing agent rules (`docs/agent-rules.md`) injected via `npx webhook-kit init-agent`.
- `dist/`: Build output (ESM `.mjs`, CJS `.js`/`.cjs`, and `.d.ts`/`.d.mts`/`.d.cts`) generated by `tsdown`.

## Build, Test, and Development

- Install: `pnpm install`
- Lint & Typecheck: `pnpm lint` — runs `oxlint`, `eslint` (statement spacing, complexity ≤ 7, banned Node built-in imports), `prettier --check`, and `tsc -p tsconfig.lint.json --noEmit` across `src/`, `tests/`, and `tests-d/`.
- Format: `pnpm format` — runs `eslint --fix` and `prettier --write .`.
- Build: `pnpm build` — bundles via `tsdown` into `dist/`.
- Test (runtime): `pnpm test` — runs Vitest specs in `tests/`.
- Test (types): `pnpm test:types` — runs `tsd` compile-time type tests in `tests-d/`.
- Test (package sandbox): `pnpm test:smoke` — packs a `.tgz` tarball and verifies zero dependencies, ESM imports, and CLI execution in an isolated temp consumer directory.

## Branch Naming & Git Conventions

All branches **MUST** follow `<category>/<kebab-case-slug>` per `CONTRIBUTE.md`. CI enforces this pattern on every pull request:

- `feat/<topic>` — New feature or provider (e.g., `feat/crypto-subtle`, `feat/stripe-provider`)
- `fix/<topic>` — Bug fix (e.g., `fix/timing-mismatch-length`)
- `docs/<topic>` — Documentation updates
- `test/<topic>` — Adding or enhancing tests
- `refactor/<topic>` — Refactoring without behavioral change
- `chore/<topic>` — Tooling, CI, or dependency updates

> **Important for Linear CLI users/agents**: Never use the default username-prefixed branch generated by `linear issue start` (such as `username/web-7-...`). Always pass `-b <category>/<topic>` (e.g., `linear issue start WEB-7 -b feat/crypto-subtle`) or create the compliant branch explicitly with `git checkout -b feat/<topic>`.

### Commit Messages

Strictly follow [Conventional Commits](https://www.conventionalcommits.org/):

- Format: `type(scope): imperative description` (lowercase `type` and `scope`, imperative verb, no trailing period).
- Examples: `feat(crypto): implement universal web cryptography primitives`, `chore(lint): enforce statement padding and complexity limits`.

## Coding Style, Spacing & Overloads

- **Universal Web Standards Only**: Never import `node:crypto`, `crypto`, `node:buffer`, or `buffer` in `src/`. Always use `globalThis.crypto.subtle`, `Uint8Array`, `TextEncoder`, `TextDecoder`, `Request`, and `Headers`.
- **Vertical Spacing**: Always leave a blank line between top-level declarations, types, interfaces, exports, and function overload signatures. Never stack multi-line function overloads without blank lines between them (enforced by `@stylistic/padding-line-between-statements`).
- **Overload Discipline**:
  - Prefer concise union parameters over exploding combinatoric overload declarations when the return type is identical.
  - Order overloads from the most specific return-type narrowing signature to the broadest fallback signature.
- **Cyclomatic Complexity**: Keep functions focused and small (`complexity` ≤ 7, enforced by `oxlint` and `eslint`). Extract named helper functions rather than nesting deep conditionals.

## Documentation & Comments (`is-kit` Standard)

- **Purpose**: Add JSDoc to public APIs and `// WHY:` comments to non-obvious implementations. Leave enough intent so future readers do not have to guess.
- **Contract JSDoc**: One-line summary + `@param` / `@returns` on public exports. Use `@example` only when it materially clarifies usage. Do not restate what TypeScript types already make obvious.
- **`// WHY:` Comments**: Explain _why_ a design or implementation choice exists (security invariant, side-channel prevention, runtime quirk, DOM/TS typing constraint). Place directly above the target code. Never write comments that merely narrate what the next line of code does.

Example — Contract JSDoc + `// WHY:` comment:

```ts
/**
 * Constant-time comparison between two buffers or strings to prevent timing side-channel attacks.
 *
 * @param a First byte array or string.
 * @param b Second byte array or string.
 * @returns `true` if byte sequences are identical, `false` otherwise.
 */
export function timingSafeEqual(
  a: Uint8Array | string,
  b: Uint8Array | string,
): boolean {
  const bufA = typeof a === "string" ? new TextEncoder().encode(a) : a;
  const bufB = typeof b === "string" ? new TextEncoder().encode(b) : b;

  const lenA = bufA.length;
  const lenB = bufB.length;
  // WHY: Seed `mismatch` with length inequality and still iterate across `maxLen`
  // so mismatched-length inputs do not short-circuit and leak length via timing.
  let mismatch = lenA === lenB ? 0 : 1;
  const maxLen = Math.max(lenA, lenB);

  for (let i = 0; i < maxLen; i++) {
    const byteA = i < lenA ? bufA[i]! : 0;
    const byteB = i < lenB ? bufB[i]! : 0;
    mismatch |= byteA ^ byteB;
  }

  return mismatch === 0;
}
```

### Webhook Signature Verification Rules (webhook-kit)

- **NEVER parse JSON before verifying signatures**: In frameworks like Next.js, Hono, or Express, parsing JSON reorders keys and strips whitespace, invalidating cryptographic HMAC checks. Always pass the raw `Request` or raw text string.
- **Constant-Time Verification**: Never compare signatures with `===` or `!==`. Always use `timingSafeEqual` or `verifyWebhookSignature` from `@amirabaris/webhook-kit`.
- **Zero Node-Only Crypto**: Web standard environments (Cloudflare Workers, Next.js Edge, Bun, Deno) do not support `node:crypto`. Rely on `@amirabaris/webhook-kit` which uses `crypto.subtle`.
- **Conventional Commits**: Follow `type(scope): message` (e.g. `feat(stripe): add tolerance check`).
